# commit

변경사항을 분석해 컨벤션에 맞는 커밋으로 저장한다. 승인 없이 커밋하지 않는다.

## 절차

### 1. 변경사항 분석

- `git rev-parse --is-inside-work-tree`로 git 저장소인지 먼저 확인한다. 아니면 중단하고 사용자에게 알린다.
- `git status --short`로 변경 파일 목록을 확인한다.
- `git diff`(unstaged), `git diff --staged`(staged)로 내용을 읽는다. 새 파일(untracked)은 직접 열어 확인한다.
- `git log --oneline -10`으로 기존 커밋 스타일을 참고한다.
- 변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

### 2. 논리적 단위로 분류

- 한 커밋은 한 가지 목적만 담는다. 서로 다른 목적(예: 기능 추가와 포맷 정리)이 섞여 있으면 나눈다.
- 같은 목적의 코드, 테스트, 스타일 변경은 한 커밋으로 묶는다.
- 파일 하나 안에 목적이 섞여 있으면 `git add -p`는 쓸 수 없으므로(대화형), 나눌 수 없다고 알리고 사용자에게 묶을지 물어본다.
- 다음 파일은 커밋 대상에서 제외하고 사용자에게 알린다: `.env`, 키·토큰이 들어간 파일, `node_modules/`, `dist/` 같은 빌드 산출물.

### 3. 커밋 메시지 작성

형식: `type: 요약`

| type | 사용 시점 |
| --- | --- |
| feat | 사용자에게 보이는 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 잡무 |

- 요약은 한국어로, 50자 안팎의 한 줄로 쓴다. 마침표는 붙이지 않는다.
- "무엇을 했는지"가 아니라 "무엇이 달라졌는지"를 쓴다. 예: `feat: 컴포넌트 카드에 코드 복사 버튼 추가`
- 이유나 맥락이 필요하면 빈 줄 뒤에 본문을 짧게 쓴다.
- 하니스가 커밋 말미에 붙일 문구(예: Co-Authored-By)를 지정했다면 본문 맨 끝에 그대로 덧붙인다.

### 4. 사용자 승인

커밋 전에 아래를 한 번에 보여주고 승인을 받는다.

- 커밋별 메시지
- 커밋별 포함 파일 목록
- 제외한 파일과 그 이유

사용자가 수정을 요청하면 반영해서 다시 보여준다. 명시적인 승인이 있을 때만 다음 단계로 간다.

### 5. 커밋 실행

- 승인된 커밋 순서대로 파일을 지정해 `git add <파일...>` 후 `git commit`을 실행한다. `git add -A`나 `git add .`는 쓰지 않는다.
- 여러 줄 메시지는 heredoc으로 전달한다.
- hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 고친 뒤 새 커밋으로 만든다.
- 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여준다.

## 하지 않는 것

- 승인 없이 커밋하지 않는다.
- `git push`, `git commit --amend`, `git reset`은 사용자가 따로 요청할 때만 한다.
- 변경하지 않은 코드를 건드리거나 커밋 중에 코드를 고치지 않는다. 문제를 발견하면 알리기만 한다.
